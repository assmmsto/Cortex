# ⚖️ الدستور الصارم — وكيل المعرفة والتنفيذ المستقل

> **الحالة:** دستور ملزم. أي عمل يخالفه يُرفض.
> **النطاق:** كل مرحلة، كل ملف، كل أداة، كل واجهة.
> **المصدر:** دمج «الوثيقة الأساسية» + «المواصفة الموحدة» + نتيجة فحص الكود الفعلي.
> **قاعدة الحفاظ:** أي فكرة جديدة تُدمج في مكانها الصحيح. أي تعارض يُوثَّق ويُحسم — لا يُسقط أحد الطرفين بصمت.

---

# الباب الأول — الهوية

## المادة 1 — ما نبنيه

نبني **وكيل معرفة وتنفيذ عام**، محلي أولًا، متعدد النماذج، متكامل مع بيئات الوكلاء الخارجية.

**ليس** مفكرة. **ليس** روبوت محادثة. **ليس** نظام أتمتة.

منظومة واحدة تجمع: قاعدة معرفة محلية مترابطة + وكيل عام ينفّذ + محادثة مرتبطة بالأدلة + خريطة علاقات واعتماديات + استيراد واسع + تكامل MCP ثنائي + ذاكرة طويلة الأجل وسجل + خصوصية وصلاحيات وتحقق وتراجع.

## المادة 2 — الثابت الذي لا يُسأل عنه

> **المفكرة جزء من الوكيل، وليست الوكيل نفسه.**

أي تصميم يعامل النظام كله كـ «ملاحظات» **مرفوض**. أي قرار يُبنى على «كل شي ملاحظة» **مرفوض**.

## المادة 3 — تعريف النجاح

النظام ليس ناجحًا لأن واجهته جميلة أو نماذجه قوية.  
**النظام ناجح فقط لأنه ينفّذ المادة 41 (الاختبار المرجعي) من البداية للنهاية.**

## المادة 4 — تعريف الفشل

يُعدّ العمل فاشلاً إذا:
- ادّعى نجاحًا بلا دليل فعلي
- عرض بيانات وهمية أو نماذج غير موجودة
- أعلن إتمام مهمة لم تُتحقق
- تجاوز صلاحية أو غيّر سياسة أمان بنفسه

# الباب الثاني — نموذج العناصر (الأساس)

## المادة 5 — لكل نوع كيان مستقل

**ممنوع** تمثيل كل شيء بجدول واحد. لكل نوع من الأنواع الثمانية **نموذج بيانات مستقل، وعمليات مناسبة له، وقواعد خاصة به**، مع القدرة على الربط ببقية الأنواع.

| # | النوع | نموذج البيانات | العمليات |
|---|---|---|---|
| 1 | **الملاحظات** | نص + وسوم + سجل تغييرات | كتابة، تعديل، ربط، وسم، تاريخ |
| 2 | **المشروعات** | أهداف، حالة، مسؤوليات، **دورة حياة** | إنشاء، تقدّم، إغلاق، أرشفة |
| 3 | **المستندات** | مصدر، نوع، **إصدارات**، بصمة | استيراد، قراءة، مقارنة، استخراج، إصدار |
| 4 | **الملفات** | مسار، مِلكية، بيانات وصفية، مصدر | حفظ، معاينة، **تحقق سلامة** |
| 5 | **المستودعات** | فروع، إصدارات، شجرة، **اعتماديات** | تحليل، diff، أثر تغيير |
| 6 | **المهام** | خطة، حالة، نتائج، تبعيات | تخطيط، تنفيذ، **استئناف** |
| 7 | **القرارات** | **سبب، أدلة، بدائل، صاحب، تاريخ اعتماد** | تسجيل، مراجعة، ربط |
| 8 | **المعرفة** | مفاهيم، حقائق، استنتاجات، مصادر | استخراج، تحقق، ربط |

## المادة 6 — أنواع المعرفة لا تُخلط ⚠️

**ممنوع** تحويل نتيجة ينتجها الوكيل تلقائيًا إلى حقيقة دائمة.

| النوع | المعنى | الثقة |
|---|---|---|
| `imported` | مستوردة من مصدر خارجي | حسب المصدر |
| `inferred` | استنتاج ولّده الوكيل | غير مؤكدة — تحتاج تحقق |
| `decided` | قرار **اعتمده إنسان** | معتمدة |
| `hypothesis` | فرضية تحتاج تحقق | **صفر — لا تُستخدم كدليل** |

كل عنصر معرفي **يجب** يحمل نوعه. **ممنوع** عرض استنتاج كأنه حقيقة.

## المادة 7 — العلاقات ليست مجرد روابط

كل علاقة **يجب** تحمل:
```
{ source, target, kind,
  provenance: {  // المصدر
    origin,        // من وين استُخرجت
    extractedAt,   // وقت الاستخراج
    confidence     // درجة الثقة
  }
}
```

**الأنواع المطلوبة:** يعتمد على، يستمد من، نتج عن، مسؤول عن، تابع لـ، متعارض مع، خطر على، **يُختبر بـ**، **يتأثر بـ**.

## المادة 8 — الخطورة من أدلة لا من عدد

**ممنوع** حساب الخطورة من عدد الروابط وحده. الخطورة **تُشتق من**:
- نتائج الاختبارات
- حساسية البيانات
- الأثر المحتمل
- الاعتماديات الحرجة

# الباب الثالث — بوابة النماذج (متطلب أساسي)

## المادة 9 — لا ارتباط بمزود واحد

**ممنوع** ربط الوكيل بمزود أو نموذج بعينه. **يجب** وجود طبقة **Model Gateway** مستقلة.

```
        نواة الوكيل
             │
      ┌──────▼──────┐
      │Model Gateway│  ← اختيار، اتصال، توافق، حدود، أخطاء
      └──┬───┬───┬──┘
         │   │   └─ موصلات مخصصة
         │   └───── سحابي (API + Base URL)
         └───────── محلي (Ollama وما شابه)
```

## المادة 10 — إضافة مزود: السلوك الإلزامي

عند إضافة مزود (اسم + `Base URL` + `API Key`)، **يجب** بالترتيب:

1. التحقق من **صحة صيغة** العنوان
2. التحقق من **إمكانية الاتصال** فعليًا
3. محاولة **جلب قائمة النماذج** من واجهة الاكتشاف
4. عرض النماذج بمعرّفاتها **الفعلية** وحالة توفرها
5. السماح بالاختيار + **تحديث القائمة** لاحقًا
6. **اختبار الاتصال بالنموذج المختار** — والتمييز بين «نجح الاتصال» و«قدر فعلاً على التوليد»
7. ربط النموذج بمهام الوكيل وفق **القدرات المثبتة**

## المادة 11 — المحرمات في بوابة النماذج 🚫

- ❌ افتراض أن كل مزود متوافق مع OpenAI
- ❌ افتراض أن كل مزود يدعم اكتشاف النماذج
- ❌ عرض نماذج وهمية
- ❌ **ادعاء نجاح الاتصال بلا اختبار فعلي**
- ❌ إرسال البيانات لمزود آخر تلقائيًا عند فشل الأساسي

**عند غياب واجهة الاكتشاف:** يُوضح النظام ذلك، ويتيح إدخال معرّف النموذج **يدويًا**، مع خيار إعادة المحاولة.

## المادة 12 — إدارة المزودين

**يجب** تسجيل **القدرات المؤكدة** لكل نموذج (سياق طويل، استخدام أدوات، رؤية) **بدل افتراضها من الاسم**.  
**يجب** تسجيل الاستهلاك والتكلفة **عند توفر بيانات موثوقة**.  
**يجب** تمكين تعطيل مزود أو نموذج **دون حذف** بقية الإعدادات.

## المادة 13 — التحويل بين النماذج مقيّد

فشل النموذج الأساسي **لا يعني** إرسال البيانات لمزود آخر. التحويل البديل **يحتاج سياسة واضحة + موافقة المستخدم + مراعاة الخصوصية**.

# الباب الرابع — الخصوصية (Local-first)

## المادة 14 — الاتجاه

**Local-first، وليس Cloud-first.** هاد مبدأ لا يُفاوض عليه.

## المادة 15 — القواعد الإلزامية

1. الملفات الأصلية وقاعدة المعرفة والفهارس وسجل المهام — **محلية افتراضيًا**
2. **الاتصالات الخارجية معطّلة افتراضيًا** — إلا ما يفعّله المستخدم صراحةً
3. لا يُرسل محتوى ملف لمزود خارجي **إلا عند اختيار وظيفة تحتاج إليه**، وبعد تطبيق سياسة الاتصال
4. **مفاتيح API محمية** — **ممنوعة** في السجلات أو المحادثات أو رسائل الأخطاء
5. **البيانات المسموح بإرسالها تُحدد لكل موصل ومهمة**، مع إمكان المراجعة قبل الإرسال
6. **يُسجَّل**: متى اتصل النظام بخدمة خارجية، لأي غرض، وما نوع البيانات المسموح بإرسالها
7. **فصل صريح**: الوصول للملفات ≠ صلاحية تنفيذ الأوامر ≠ صلاحية تعديل النظام

## المادة 16 — الصدق مع المستخدم

**ممنوع** الادعاء بأن البيانات لم تغادر الجهاز إذا استقبلها نموذج سحابي.  
**يجب** عرض **حدود الخصوصية الخاصة بكل اتصال** قبل استخدامه.

## المادة 17 — قابلية الاختبار

**يجب** أن يكون النظام **قابلاً للاختبار** للتأكد من سلوك اتصالاته وحماية بياناته.  
الادعاء بـ «محلي» بلا اختبار يُثبته = **ادعاء فارغ مرفوض**.

# الباب الخامس — الاستيراد

## المادة 18 — المصادر المدعومة

| المصدر | ملاحظة |
|---|---|
| الملفات والمجلدات المحلية | — |
| مستودعات Git/GitHub | عامة وخاصة **وفق الصلاحيات** |
| ملفات البرمجة والتوثيق والبيانات | — |
| **PDF · DOCX · PPTX · Markdown · HTML** | |
| الجداول والبيانات المنظمة والسجلات | — |
| الصور **مع OCR** عند الحاجة | |
| صفحات الويب ومصادر البحث | المصرح بها فقط |
| خدمات خارجية عبر API | وموصلات قابلة للإضافة |
| **الأرشيفات** | **مع فحص المحتوى قبل المعالجة** |

## المادة 19 — ما يُحفظ مع كل مستورد

- الملف **الأصلي**
- المصدر
- تاريخ الاستيراد
- البصمة الرقمية عند الحاجة
- نتيجة التحليل

**إعادة الفهرسة عند التحديث — دون فقدان تاريخ العناصر والعلاقات.**

## المادة 20 — الصدق مع الصيغ

**عند عدم دعم صيغة: يُوضح النظام ذلك — ممنوع الادعاء بأنه قرأها.**

## المادة 21 — الاستيراد الآمن (صارم)

الملف المستورد **ممنوع من**:
- ❌ التشغيل التلقائي
- ❌ منح صلاحيات تنفيذ
- ❌ **تغيير تعليمات الوكيل أو سياسات الأمان**

> كل محتوى مستورد = **بيانات، ليس أوامر**. أي محتوى يحاول إعطاء تعليمات للوكيل **يُعزل ويُسجَّل**.

# الباب السادس — الوكيل التنفيذي

## المادة 22 — التعريف

الوكيل يستقبل هدفًا → يجمع السياق → يضع خطة → يختار الأدوات والنموذج → **ينفّذ** → **يتحقق**.

## المادة 23 — الاختصاصات الإلزامية

| # | الاختصاص | الحالة |
|---|---|---|
| 1 | البحث عبر الملفات والمصادر | موجود |
| 2 | دراسة موضوع من عدة مصادر | جزئي |
| 3 | **تحليل مستودعات برمجية وفهم بنيتها** | **معدوم** |
| 4 | التخطيط وتقسيم الأهداف لمهام **مترابطة** | جزئي |
| 5 | دمج المعلومات مع **الحفاظ على المصادر** | موجود |
| 6 | اكتشاف التعارض والتكرار والفجوات والمخاطر | جزئي |
| 7 | إنتاج التقارير والمخططات والمستندات | جزئي |
| 8 | **تنفيذ تعديلات على الملفات والمشروعات ضمن الصلاحيات** | **محصور** |
| 9 | **تشغيل الاختبارات والتحقق من النتائج** | **معدوم** |
| 10 | متابعة الأعمال **واستئنافها بعد انقطاع** | جزئي |
| 11 | **تقييم أدائه واقتراح تحسينات واختبارها قبل الاعتماد** | **معدوم** |

## المادة 24 — ما يجب أن يمتلكه

- ذاكرة طويلة الأجل **منفصلة عن سياق المحادثة المؤقت**
- سجل للأهداف والخطط والقرارات والنتائج
- إدارة أولويات و**مهام متزامنة**
- قدرة على **استئناف العمل بعد الانقطاع**
- **آليات تحقق واختبارات قبل اعتماد النتائج**
- **صلاحيات تنفيذ محددة + مراجعة تغييرات + إمكانية تراجع**
- **تقييم الأخطاء واقتراحات تحسين قابلة للاختبار**

## المادة 25 — حدود الاستقلال

> **الاستقلال = مواصلة المهام واتخاذ خطوات تشغيلية ضمن الحدود المعتمدة.**
> **الاستقلال ≠ ذكاء غير محدود، و≠ ضمان صحة كل استنتاج.**

## المادة 26 — التحسين الذاتي المنضبط

التحسين **يجب** يمر بالدورة كاملة:
```
يكتشف مشكلة → يقترح تعديل → يجرّبه في بيئة معزولة
   → يقارن بمعايير القبول → يعتمد أو يتراجع
```

**🚫 محرم مطلقًا:** تغيير سياسات الأمان أو الصلاحيات الأساسية من تلقاء نفسه.

## المادة 27 — المحادثة

الإجابات **مرتبطة بالأدلة الفعلية**، مع **الانتقال المباشر** للملف أو الموضع.

**مثال ملزم من الدستور:** عند تحليل مشروع برمجي، **لا يكفي** قراءة README وإعطاء وصف عام. **يجب**: فهرسة المشروع + فهم العلاقات + تحديد نقاط الدخول والاعتماديات + تحليل الاختبارات → **ثم** الإجابة.

# الباب السابع — MCP (ثنائي الاتجاه)

## المادة 28 — إلزامي من البداية

**MCP ليست إضافة تُؤجل لنهاية المشروع. جزء أساسي من المعمارية منذ اليوم الأول.**

## المادة 29 — الاتجاهان

| الاتجاه | الوظيفة | الحالة |
|---|---|---|
| **MCP Client** | الاتصال بخوادم خارجية، اكتشاف الأدوات والموارد، استدعاؤها **ضمن الصلاحيات** | **معدوم** |
| **MCP Server** | تقديم المعرفة والبحث والملفات والمشروعات والمهام والأدوات **التي يسمح المستخدم بمشاركتها** | موجود |

## المادة 30 — التكاملات المستهدفة

OpenCode · Claude Code · أدوات التطوير والوكلاء المتوافقة · أي بيئة عبر MCP أو موصل متخصص.

## المادة 31 — قواعد التكامل

- ❌ الاعتماد على **أسماء التطبيقات** وحدها
- ✅ **اكتشاف القدرات الفعلية** — ليس كل تطبيق ينفّذ كل عملية
- ⚠️ **اتصال MCP لا يعني صلاحية الوصول لكل ملفات النظام**
- ⚠️ **اتصال MCP لا يضمن الخصوصية** — تُضبط الأدوات والموارد المسموح بمشاركتها
- ✅ **يجب اختبار التوافق والصلاحيات وطريقة الاتصال لكل تكامل**
- ✅ سجل يوضح: الأدوات المستدعاة، النتائج، الملفات التي تغيّرت، **العمليات التي تحتاج موافقة**

## المادة 33 — قاعدة الطبقات

> **ليست وكلاء مستقلين يتبادلون أوامر بلا ضوابط. مكونات لنظام واحد.**

- يمكن وجود مهارات متخصصة أو وكلاء فرعيون
- **محرك التنسيق** يدير الاعتماديات وحالة التنفيذ
- **طبقة الأمان تفرض الصلاحيات باستقلال عن النموذج**

**يعني:** القرار الأمني لا يأتي من النموذج اللغوي أبدًا.

## المادة 34 — اكتشاف معماري مؤكد

حلقة الوكيل الحالية (`thought → action → tool → result`) **سليمة**، وتسجيل الأدوات **ديناميكي**.

> **النتيجة:** إضافة أداة = تسجيلها. الحلقة تستعملها بلا تعديل.
> **يعني:** التحوّل من مفكرة لوكيل = **إضافة أدوات وطبقات حماية**، ليس إعادة بناء.

# الباب التاسع — الأمان والصلاحيات

## المادة 35 — البوابات الحتمية

**🚫 ممنوع** استخدام الذكاء الاصطناعي للتحقق من:
- التوقيعات والموافقات
- حالة الصلاحيات
- بصمة الإصدار
- حالة الاتصال
- القيود الأمنية

**هاد يتحقق بخدمات برمجية مباشرة.** النموذج يُستخدم فقط حين تحتاج المهمة **فهم معنى** أو **تفسير اختلاف أدلة** أو **اقتراح معالجة**.

## المادة 36 — طابور الأحداث الدائم

**يجب** وجود: سجل أحداث دائم + **مفاتيح منع التكرار** + تسجيل الحدث وتغيير الحالة **بصورة متسقة**.

**السبب:** إذا نجح إنشاء شيء ثم تعطّل النظام قبل التسجيل — **ممنوع** إنشاؤه مرة ثانية عند إعادة التشغيل.

## المادة 37 — الصلاحيات

- كل وكيل وأداة: **أقل صلاحية لازمة**
- ممنوع الوصول غير المصرح
- **العزل** بين المشاريع
- الملفات المشبوهة **تُعزل وتُفحص في بيئة محدودة الصلاحيات**

## المادة 38 — التراجع والتدقيق

- كل تغيير **قابل للمراجعة والتراجع حيثما أمكن**
- **ممنوع** محو سجل التدقيق — يُحفظ محميًا من التعديل غير المصرح
- سجلات للعمليات والأخطاء والقرارات المهمة

# الباب العاشر — خريطة الاعتماديات

## المادة 39 — الفرق الحاسم

> **خريطة روابط ≠ خريطة اعتماديات.**

الخريطة **يجب** تجيب على 8 أسئلة:

1. ما الذي **يعتمد على** ماذا؟
2. **ما مصدر كل معلومة؟**
3. **ما العناصر التي قد تتأثر بتغيير؟**
4. ما المكونات **الأكثر مركزية أو حساسية**؟
5. ما **المخاطر المثبتة** وما **المخاطر المحتملة**؟
6. ما المسؤوليات **الموثقة**، وما **غير المحددة**؟
7. ما العناصر **المتعارضة أو المكررة**؟
8. **ما الذي تغيّر منذ آخر تحليل؟**

## المادة 40 — قواعد العرض

- **قابلة للتصفية** حسب: المشروع، نوع العنصر، الخطورة، المسؤولية، **مصدر المعلومة**
- تفاصيل العنصر **يجب** تحمل: المصدر، الإصدار، العلاقات، الأدلة، **درجة الثقة**
- **تُحدّث العلاقات** عند تغير الملفات أو ظهور نتائج تحليل جديدة

# الباب الحادي عشر — الاختبار المرجعي

## المادة 41 — إثبات أن النظام ليس مفكرة 🎯

**هذا هو المعيار الحاسم. النظام يُقاس به.**

الاختبار: **مشروع برمجي حقيقي**، 8 خطوات:

1. **استيراد مستودع كامل** — ملفات + توثيق + اعتماديات
2. **تحليل البنية** وتكوين خريطة للعلاقات **التي أُمكن التحقق منها**
3. **طرح أسئلة** عن الملفات والوظائف ومصادر المعلومات
4. **تحديد أثر تغيير** ملف أو وحدة على بقية المشروع
5. **تكليف الوكيل بتنفيذ تعديل محدد** داخل بيئة آمنة
6. **تشغيل الاختبارات** والتحقق من الفرق الناتج
7. **حفظ التقرير والقرارات والنتائج** وتحديث الخريطة
8. **إيقاف النظام وإعادة تشغيله** — والتحقق من استعادة حالة المهمة وسجلها

**بعد نجاحه:** يُوسَّع النظام للبحث العلمي، دراسة الوثائق، إدارة المعرفة المؤسسية، ومهارات أخرى.

## المادة 42 — مراحل البناء الثمانية

| # | المرحلة | معيار القبول الفعلي |
|---|---|---|
| 1 | **قاعدة المعرفة** | استيراد وحفظ وفهرسة وبحث، **مع الاحتفاظ بالأصول والمصادر** |
| 2 | **العلاقات والخريطة** | اكتشاف علاقات + **إظهار مصدرها** + الاعتماديات + التغييرات |
| 3 | **الوكيل والمحادثة** | مهام متعددة الخطوات + **الإجابة بأدلة من الملفات** |
| 4 | **بوابة النماذج** | إضافة مزود عبر API+BaseURL + اكتشاف النماذج + اختبار الاتصال |
| 5 | **التنفيذ** | تعديل ملفات + **تشغيل اختبارات** + مراجعة نتائج + **تراجع** |
| 6 | **MCP** | **استهلاك أدوات خارجية** + تقديم أدوات النظام |
| 7 | **الاستقلال التشغيلي** | متابعة مهام + استئناف + تقييم نتائج + تحسين |
| 8 | **جاهزية الشركات** | صلاحيات + تدقيق + أمان + توزيع + توثيق |

## المادة 43 — قاعدة الانتقال الصارمة

> **🚫 ممنوع الانتقال لمرحلة قبل إثبات المرحلة السابقة باختبار فعلي.**

## المادة 44 — اختبارات الفشل إلزامية

كل مرحلة **يجب** تختبر حالات الفشل:

- مزود API غير صالح
- نموذج غير متاح
- مستودع ضخم
- ملف غير مدعوم
- **انقطاع أثناء تنفيذ مهمة**
- **محاولة أداة الوصول لبيانات غير مصرح بها**

## المادة 45 — بوابات منع الإطلاق

لا يُنتقل لإصدار تالٍ إذا تحقق **أي** مما يلي:

- ثغرة حرجة مفتوحة أو إمكانية تجاوز صلاحيات
- إمكان صرف/تنفيذ مزدوج دون تحقق
- انتقال غير مسموح في آلة الحالات
- فشل عزل بيانات المشاريع أو فحص الملفات غير الموثوقة
- عدم القدرة على استعادة المهام المعلقة
- تعارض حرج بين نتائج الفحص دون مسار حل
- **فشل أحد اختبارات التراجع المعتمد**

# الباب الثاني عشر — قواعد العمل

## المادة 46 — المحرمات المطلقة 🚫

1. **ممنوع** ادعاء نجاح بلا دليل فعلي
2. **ممنوع** عرض بيانات وهمية أو نماذج غير موجودة
3. **ممنوع** الادعاء بأن النظام قرأ صيغة لا يدعمها
4. **ممنوع** تحويل استنتاج الوكيل إلى حقيقة دائمة
5. **ممنوع** تغيير سياسات الأمان أو الصلاحيات ذاتيًا
6. **ممنوع** محو أثر تدقيقي
7. **ممنوع** منح صلاحية تنفيذ لمحتوى مستورد
8. **ممنوع** الانتقال لمرحلة قبل إثبات السابقة
9. **ممنوع** ترك محتوى مستورد يغيّر تعليمات الوكيل
10. **ممنوع** الاعتماد على النموذج في قرار أمني

## المادة 47 — الالتزامات المطلقة ✅

1. كل ادعاء **معه دليل** قابل للتحقق
2. كل علاقة **معه مصدر ووقت وثقة**
3. كل عنصر **معه نوعه** (مستورد/استنتاج/قرار/فرضية)
4. كل تنفيذ **معه سجل**
5. كل تغيير **معه إمكانية تراجع**
6. كل مهمة **معها قدرة استئناف**
7. كل صيغة غير مدعومة **يُعترف بها صراحة**
8. كل اختبار قبول **يشمل حالات الفشل**

## المادة 48 — عند تعارض فكرتين

**نوثّق التعارض ونحسمه — لا نسقط إحداهما بصمت.**
